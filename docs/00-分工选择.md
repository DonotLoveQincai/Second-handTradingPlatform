# 00 · 四个分工，怎么选

> 四个人对着这张表各挑一个。挑完在群里报一句"我要 X"，然后按对应任务表往下做。
> **选人比选技术重要**：分工不公平是这类作业最常见的翻车原因，不是代码写不出来。

---

## 一、速选表（30 秒看完）

| | **A 商品域** | **B 用户与订单** | **C 交易状态** | **D 平台底座** |
|---|---|---|---|---|
| 一句话 | 商品能发布、能搜、能下架 | 谁能登录、谁买什么、记录查得出 | 订单一步步往下走，每步留痕 | 仓库、数据库、窗口、把大家拼起来 |
| 代码量 | 中（约 650 行） | **最多**（约 950 行） | 少（约 460 行） | 中偏多（约 720 行） |
| 逻辑难度 | ★★☆ | ★★★☆ | **★★★★★** | ★★★ |
| 界面工作量 | **最多**（3 页 + 1 框） | 多（2 页 + 3 框） | 少（1 页） | 中（1 页 + 主窗口） |
| 用到的技术 | SQL 动态条件、表格显示 | 跨域事务、密码哈希、JOIN | 状态机、权限判断、事务 | qmake/`.pri`、建表脚本、信号连接 |
| 第 0 周忙不忙 | 轻松（写头文件） | 轻松（写头文件） | 轻松（写头文件） | **最忙，必须提前交付** |
| 出错最典型的坑 | 状态改了列表不刷新 | 事务忘了 rollback | 日志顺序乱、按钮该有没有 | 少拷一个 dll 全班跑不起来 |
| 适合谁 | 想看到东西、喜欢调界面的 | 想管全局、愿意多写一点的 | 喜欢想清楚逻辑的、数学/算法好的 | 环境最强、愿意当组长协调的 |
| 答辩讲什么 | SQL 注入防护 + 条件更新 | 跨域事务 + 防重复下单 | 5×4 状态机 + 穷举自检 | 组合根 + 页面靠信号通信 |

**难度排序**：C > B > D > A　　**代码量排序**：B > D > A > C

## 二、四张角色卡

### 🅰 A · 商品域（上架 / 下架 / 检索）

**你负责的一半功能表**：功能①

你要写的东西（7 个文件对）：
- `core/entity/product.h`、`core/repository/i_product_repository.h`
- `data/product_dao.{h,cpp}` —— 增、改状态、查单条、条件搜索、（按卖家查）
- `services/product_service.{h,cpp}` —— 发布校验、下架权限
- `ui/pages/product/search_page`（检索页）、`publish_dialog`（发布框）、`my_products_page`（我的商品）

**你一个人要独立完成的核心代码**：
```cpp
UPDATE products SET status=? WHERE id=? AND status=?   // 检查影响行数
```

**别人会来找你的场景**：B 下单要占商品（`ON_SALE → SOLD`）、C 取消订单要把商品放回在售（`SOLD → ON_SALE`）、订单取消后商品没回来。

**验收就三条**：搜得到、搜得准（关键字/分类/价格/排序）、只有自己的能下架。

**为什么适合新手**：改一行 SQL/一个界面立刻看得见结果，第 1 周周末就有能跑的东西，不容易放弃。

---

### 🅱 B · 用户与订单（登记 / 下单 / 订单记录）

**你负责的一半功能表**：功能②

你要写的东西（11 个文件对，最多的一个）：
- `core/entity/{user.h, order.h}`、`core/session.h`、两个接口
- `data/user_dao`（含密码哈希）、`data/order_dao`
- `services/auth_service`、`services/order_service`（**下单事务在这里**）
- `ui/pages/auth/login_dialog`、`ui/pages/order/{my_orders_page, buy_dialog, order_detail_dialog}`

**你一个人要独立完成的核心代码**：
```cpp
db.transaction();
  order.insert();                       // 你的表
  product.updateStatus(ON_SALE, SOLD);  // 别人的表
  log.insert();                         // 第三个人的表
db.commit();
```

**评审重点**：这段事务里任何一步失败都必须 `rollback()`，一条都不能漏。

**验收就三条**：注册登录通、下单成功后商品消失、连点两次只有一条订单。

**为什么它最"重"**：页面最多（登录、我的订单、购买确认、订单详情四个），而且只有你同时碰三张表。想少写点就选别的。

---

### 🅲 C · 交易状态（流转 / 跟踪 / 记录查询）

**你负责的一半功能表**：功能③

你要写的东西（6 个文件对，最少的）：
- `core/entity/trade_log.h`、`core/repository/i_trade_log_repository.h`
- `data/trade_log_dao`
- `services/trade_state_machine`（**纯静态，最容易拿分**）、`services/trade_service`
- `ui/pages/trade/trade_log_page`

**你一个人要独立完成的核心代码**：
```cpp
// 一张表表达全部规则：当前状态 → (动作 → 目标状态)
{ PENDING_PAY, { {PAY, PAID}, {CANCEL, CANCELLED} } },
{ PAID,        { {SHIP, SHIPPED}, {CANCEL, CANCELLED} } },
{ SHIPPED,     { {CONFIRM, COMPLETED} } },
```
外加 `selfCheck()`：穷举 5 状态 × 4 动作 = 20 组，断言合法转移恰好 5 条。

**别人会来找你的场景**：B 的订单详情页按钮显示什么，完全由你的 `actionsFor()` 决定；点了能不能成功由你的 `checkPermission()` 决定。

**验收就三条**：四步流转走通、非法动作被拦、日志顺序正确。

**为什么代码最少但最难**：状态机、权限规则、事务三件事绞在一起，写错一个分支答辩现场就会卡住。逻辑想不清的人不要选。但写对了是整个项目最出彩的部分。

---

### 🅳 D · 平台底座（骨架 / 数据库 / 组装 / 导入）

**你负责的一半功能表**：功能④ + 把前三个人拼到一起

你要写的东西（8 个文件对 + 配置文件）：
- `.gitignore`、`.pro`、4 个 `.pri`、`sql/001_init.sql`、`ui/resources/resources.qrc`
- `core/common/{opresult.h, constants.h}`
- `data/db_manager`、`ui/mainwindow`（**只有你能改**）
- `services/import_service`、`ui/pages/import/import_page`
- `main.cpp`、打包

**你一个人要独立完成的核心代码**：
```cpp
void MainWindow::buildServices();   // 全项目唯一 new 对象的地方（组合根）
void MainWindow::connectBus();      // 全项目唯一 connect 的地方
```

**你的时间压力最大**：第 0 周别人只写头文件，你必须五天交付"仓库 + 分支保护 + `.gitignore` + 4 个 `.pri` + 建表 SQL + `DbManager` + 能跑的空窗口"，否则三个人第 1 周无事可做。

**验收就三条**：别人 `git clone` 后 F5 就出窗口、删库重跑自动建表、拷到没装 Qt 的电脑能开。

**为什么建议给组长**：你要 review 所有人的 PR、要改契约、要主持联调、要打包。技术门槛不高，但**不能拖**。

---

## 三、三条分配原则

1. **D 先定，而且要定给最靠得住的人**。D 晚一天，另外三个人的第 1 周就空一天。D 的技术可以不是最好的，但必须是最不会拖的。
2. **C 不要给最没时间的人**。C 代码量最少，容易被当成"轻松位"塞给别人，实际上它决定答辩能不能讲清楚。让逻辑最清楚的人做。
3. **A 给新手，但要配个 review 的人**。A 见效快、有成就感，适合第一次做 Qt 的人；让 C 或 D 帮他 review DAO（因为 A 的 `updateStatus` 是 B 和 C 都依赖的，写错会连锁）。

---

## 四、两种不建议的分法

| 分法 | 为什么不行 |
|---|---|
| **按页面分**（你做检索页、我做订单页……） | 一个页面里往往要碰别人的表和别人的服务，两个人在同一页面里写，改一行就冲突；而且没人对"数据一致性"负责 |
| **按时间分**（第 1 周我做、第 2 周你做） | 每个人都要重新理解别人的代码，等于四个人的活一个人干四遍；提交记录也证明不了谁负责什么 |

**为什么按业务域分好**：一个域里从表到界面都由一个人负责，他可以自己从头到尾跑通，出问题不用跨人排查；域和域之间只有 4 个接口和几处信号，接口定了就能并行。

---

## 五、选完之后的三件事（当天做完）

1. 在群里报："我要 A / B / C / D"，D 记到 `docs/meetings/` 第一次记录里
2. 各自改名：分支 `feature/A-product` 等四个已经定好，**不要改名字**（D 的分支保护规则按这个配）
3. 每人打开自己的任务表，把「任务清单」表格里第 0 周的几项勾掉，然后只做第 0 周的事——**第 0 周不碰业务代码**

---

## 六、如果人数有变化

| 情况 | 怎么办 |
|---|---|
| 只有 3 个人能干 | 砍掉 A，商品域并入 C（检索 + 下架 + 状态一起做）；D 的导入页降级为"用 SQL 插演示数据"，不做 CSV |
| 有 5 个人 | 把 B 拆成"用户与登录"（`user_dao` / `auth_service` / 登录框）和"订单"（`order_dao` / `order_service` / 订单三个界面），其他人不动 |
| 有人明显跟不上 | 把他从 C 调到 A（A 有即时反馈，容易坚持），C 交给原 A 的人，两个人换一下即可，文件归属表跟着改一行 |
